# Working rules for this repo

This is a personal medical records app (private health journal). The feature plan lives in ROADMAP.md.
For the monitoring items (mon-*), docs/MONITORING.md sections 14 and 15 hold the plan, the guardrails and what
stays with me.

## How to implement a roadmap item
1. Read ROADMAP.md and the item asked for. Check its "Depends on" items are done (checked). If not, stop and tell me.
2. Explore the relevant code first. For items in Level 3 or above, present a short plan (data model changes, files to touch, UI changes, migration needs) and WAIT for my approval before coding.
3. Start a branch from an up-to-date main before changing anything (see "Git workflow"). Never work on main.
4. Keep changes scoped to the item. No unrelated refactors. Reuse existing components, tokens and patterns.
5. Never lose or corrupt existing user records. Any data model change needs a migration with default values for existing records.
6. Run the app and check the change at 360px and 430px widths. Run existing tests/lint/build if they exist, and add tests for new logic. Test data must follow "Test data and screenshots".
7. Commit on the branch with the message "feat(#N): <title>" (or "fix(#N)"). One item per branch; small series of commits is fine.
8. In ROADMAP.md, on the same branch, tick the item's checkbox and add a one-line "Notes:" entry under it (what was built and anything deferred).
9. Push the branch and open a pull request to main with `gh pr create`, filling in the pull request template.
10. Stop there. Do not merge. Finish with a short summary: what changed, how to test it, the PR link, any follow-ups.

## Git workflow
- Branch names: `feat/<N>-<short-name>`, `fix/<N>-<short-name>`, `chore/<short-name>` or `docs/<short-name>` (lowercase, hyphens).
- Start every branch with: `git switch main`, `git pull --ff-only`, `git switch -c <branch>`.
- If you notice you are on main with uncommitted changes, move them to a new branch with `git switch -c <branch>` before committing. Never commit on main.
- Never push to main, never force-push, and never rewrite history that is already pushed.
- Never merge, approve or close pull requests. I review and merge every PR myself.
- Never skip checks: no `--no-verify`, never disable or weaken CI, branch protection, tests or lint rules to make something pass.
- If CI fails on your PR, fix it on the same branch and push again. If you can't fix it, tell me why.
- Before every commit, run `git status` and review the staged files. Never commit `.env` files, anything under `data/`, database files, backups, exports, Terraform state or `*.tfvars`.
- Changes to `.github/workflows/`, `.claude/settings.json` or `infra/` need my explicit approval first, and the PR description must call them out.
- Never deploy, SSH into servers, or change anything on staging or production. Deployment happens only through the pipeline.

## Privacy rules (health data)
- Never send record data, attachments or personal info to any third-party service unless the roadmap item explicitly requires it and I approved it.
- Never log record contents to the console in production code.

## Test data and screenshots
This repository is public. Anything committed is visible to everyone, permanently.
- All test data is synthetic: names, emails, phone numbers, dates, doctors, labs, diagnoses, medicines and lab values are invented.
- Emails use `@example.com` (as backend/tests/conftest.py already does). Names are obviously fictional, e.g. "Test Patient One", "Dr. Sample Doctor".
- Phone numbers in tests are clearly fake and never receive messages. Tests never send real SMS or email; use the provider's test numbers or sandbox mode.
- Test files (PDF, PNG, JPEG, HEIC) are generated by code or made by hand, and say "SAMPLE - NOT A REAL RECORD" where the format allows. Never use a real report, prescription, scan or photo, even redacted or blurred.
- Screenshots (Playwright, PRs, docs) are taken only from a throwaway test database with synthetic data. Never from production, staging, or a database copied from either.
- Never copy production or staging databases, backups or exports to this laptop or into the repository, and never restore one into a dev environment.
- If you are given or find something that looks like real personal or health data, stop, don't commit it, and tell me.
- New test files go in `frontend/e2e/fixtures/` or `backend/tests/`, following the README there.
